01 · 从进程替换说起

平时使用 cat 时，我们可以传入一个文件名，让它读取文件内容。如果数据并不存在于磁盘文件中，而是由另一条命令动态产生，又该怎么办？

file=$(mktemp)
printf 'hello\n' > "$file"
cat "$file"
rm -- "$file"
# 输出：hello

Bash 提供了另一种写法，无须事先创建普通文件：

cat <(printf 'hello\n')
# 输出：hello

这就是进程替换（process substitution）。表达式 <(command) 将命令的标准输出通过一个可供读取的路径暴露出来。外层命令接收到的是路径，而不是命令输出的字符串。注意，< 与左括号之间不能有空格。

例如，用 printf 查看 Bash 实际生成的参数：

printf '%s\n' <(printf 'hello\n')
# 可能输出：/dev/fd/63
printf
标准输出
匿名管道
通过 /dev/fd/63 暴露读端
cat
打开路径

在支持 /dev/fd 的 Linux 环境中，Bash 通常借助匿名管道实现进程替换；其他环境也可能使用命名管道。这里讨论前一种实现。

与命令替换、普通管道有什么不同？

写法外层命令接收到什么
printf '%s\n' "$(printf hello)"字符串 hello（命令替换）
printf '%s\n' <(printf hello)一个路径，例如 /dev/fd/63（进程替换）
printf hello | catcat 的标准输入连接到管道

进程替换尤其适合需要文件名参数的程序。例如 diff <(printf 'A\n') <(printf 'B\n') 可以直接比较两条命令产生的数据。

02 · 让进程替换停留在可观察状态

前面的 printf 和 cat 很快就结束了，来不及检查它们的文件描述符。于是把产生数据的命令换成 sleep：

cat <(sleep 10)

这里必须给 sleep 指定时间；单独写 sleep 会因缺少参数而退出。预测一下：sleep 不产生任何标准输出，cat 会立即结束，还是等待 10 秒？

答案是等待。sleep 虽然没有写入任何字节，却仍持有管道的写端。cat 尝试读取空管道时，只要还有写端未关闭，就不能把暂时没有数据当成文件结束。

为了获得足够长的观察时间，在 Bash 终端中执行以下命令（后台运行便于在同一终端检查）：

cat <(sleep 10000) &
pid=$!
ps -p "$pid" -o pid,ppid,args
ls -l "/proc/$pid/fd"

如果刚启动时尚未看到预期结果，稍等片刻后再次执行 ls。也可以在前台运行 cat <(sleep 10000)，再从另一终端观察对应的 PID。实验完成后应结束 cat 和本次实验对应的 sleep 进程，不要误杀其他同名进程。

03 · cat 持有同一管道的两个文件描述符

原本只想观察一个管道，却发现 cat 的文件描述符表中出现了两个指向同一管道的条目。

可能看到如下结果（编号仅为示例）：

3  -> pipe:[18490]
63 -> pipe:[18490]

为什么同一个进程会持有同一管道的两个读端描述符？关键在于 Bash 的进程替换机制，以及 cat 打开输入文件的方式。严格来说，管道由 Bash 创建，而非 sleep。

匿名管道1
cat 读端描述符2
继承描述符（示例）63
新打开描述符（示例）3

04 · 还原执行过程

第一步，Bash 创建匿名管道，并将读端安排在一个较高编号的文件描述符上，例如 63。第二步，Bash 启动进程替换中的命令，将管道写端连接到 sleep 的标准输出。第三步，Bash 将进程替换表达式展开为 /dev/fd/63，并启动 cat，使其继承描述符 63。

cat /dev/fd/63

对 cat 而言，这只是一个普通的文件名参数。它并不知道 Bash 已经打开了这个管道，于是再次调用 open 或 openat：

int fd = open("/dev/fd/63", O_RDONLY);

内核分配当前最小的可用文件描述符，通常为 3。此时 cat 同时持有继承而来的 fd 63 和自己打开的 fd 3，但实际通过 fd 3 读取数据。

sleep: fd 1 (写端) ──┐
                     ├── pipe:[18490]
cat:   fd 63 (读端) ─┤
       fd 3  (读端) ─┘

05 · 用系统调用跟踪验证

strace -f -yy \
  -e trace=pipe,pipe2,dup2,fcntl,execve,openat,read,close \
  bash -c 'cat <(sleep 10000)'

重点观察以下系统调用（示意输出，并非本次实测日志）：

execve("/usr/bin/cat", ["cat", "/dev/fd/63"], ...)
openat(AT_FDCWD, "/dev/fd/63", O_RDONLY) = 3<pipe:[18490]>
read(3<pipe:[18490]>, ...

sleep 不写入数据，却仍持有写端，因此 cat 的 read 调用阻塞，直到有数据可读或所有写端关闭。实验结束可按 Ctrl+C。

06 · 对照三种写法

命令cat 读取数据所用描述符连接方式
sleep 10000 | cat0Bash 直接连接标准输入
cat < <(sleep 10000)0Bash 处理输入重定向
cat <(sleep 10000)通常为 3cat 自行打开路径，同时继承 fd 63

具体描述符编号及额外描述符是否保留取决于 Bash 版本和运行环境。

07 · 重新打开与复制描述符是一回事吗？

在 Linux 上，不是。dup(63) 产生一个指向同一打开文件描述（open file description）的新描述符，而 open("/dev/fd/63", O_RDONLY) 对匿名管道通常创建一个新的打开文件描述。两者仍指向同一个内核管道对象。

fd 63↓struct file A
fd 3↓struct file B
↘　　　　　　　　　↙同一个内核管道对象共享缓冲区
比较项dup(63)重新 open
新文件描述符是是
新打开文件描述否是
共享文件状态标志是否
共享管道缓冲区是是

例如，利用 fcntl 修改 fd 3 的 O_NONBLOCK 标志，不会因此改变独立打开的 fd 63 的对应标志。但从任一描述符读取数据，都会消耗同一管道缓冲区中的字节，并不会获得两份数据。

08 · 从现象到本质

这个实验揭示了三个不同层次：文件描述符是进程中的整数索引；打开文件描述是内核中记录打开状态的对象；管道对象则是实际承载数据的共享资源。共享底层资源，不意味着共享打开文件描述；共享打开文件描述，也不意味着文件描述符编号相同。

思考题：如果关闭 fd 63，fd 3 还能继续读取吗？如果分别从两个描述符读取一个字节，第二次读到的是同一个字节还是下一个字节？先预测，再通过实验验证。
