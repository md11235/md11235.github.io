为什么 cat 持有同一管道的两个文件描述符？

2026-11-26 · Bash 内部机制观察

一、从一个现象出发

cat <(sleep 10000)

在另一个终端中查看 cat 的文件描述符：

pid=$(pgrep -n -x cat)
ls -l /proc/$pid/fd

可能看到如下结果（编号仅为示例）：

3  -> pipe:[18490]
63 -> pipe:[18490]

为什么同一个进程会持有同一管道的两个读端描述符？关键在于 Bash 的进程替换机制，以及 cat 打开输入文件的方式。严格来说，管道由 Bash 创建，而非 sleep。

二、还原执行过程

第一步，Bash 创建匿名管道，并将读端安排在一个较高编号的文件描述符上，例如 63。第二步，Bash 启动进程替换中的命令，将管道写端连接到 sleep 的标准输出。第三步，Bash 将进程替换表达式展开为 /dev/fd/63，并启动 cat，使其继承描述符 63。

cat /dev/fd/63

对 cat 而言，这只是一个普通的文件名参数。它并不知道 Bash 已经打开了这个管道，于是再次调用 open 或 openat：

int fd = open("/dev/fd/63", O_RDONLY);

内核分配当前最小的可用文件描述符，通常为 3。此时 cat 同时持有继承而来的 fd 63 和自己打开的 fd 3，但实际通过 fd 3 读取数据。

sleep: fd 1 (写端) ──┐
                     ├── pipe:[18490]
cat:   fd 63 (读端) ─┤
       fd 3  (读端) ─┘

三、用系统调用跟踪验证

strace -f -yy \
  -e trace=pipe,pipe2,dup2,fcntl,execve,openat,read,close \
  bash -c 'cat <(sleep 10000)'

重点观察以下系统调用（示意输出，并非本次实测日志）：

execve("/usr/bin/cat", ["cat", "/dev/fd/63"], ...)
openat(AT_FDCWD, "/dev/fd/63", O_RDONLY) = 3<pipe:[18490]>
read(3<pipe:[18490]>, ...

sleep 不写入数据，却仍持有写端，因此 cat 的 read 调用阻塞，直到有数据可读或所有写端关闭。实验结束可按 Ctrl+C。

四、对照三种写法

命令cat 读取数据所用描述符连接方式
sleep 10000 | cat0Bash 直接连接标准输入
cat < <(sleep 10000)0Bash 处理输入重定向
cat <(sleep 10000)通常为 3cat 自行打开路径，同时继承 fd 63

具体描述符编号及额外描述符是否保留取决于 Bash 版本和运行环境。

五、重新打开与复制描述符是一回事吗？

在 Linux 上，不是。dup(63) 产生一个指向同一打开文件描述（open file description）的新描述符，而 open("/dev/fd/63", O_RDONLY) 对匿名管道通常创建一个新的打开文件描述。两者仍指向同一个内核管道对象。

cat fd 63 ── struct file A ──┐
                             ├── 同一个管道及缓冲区
cat fd 3  ── struct file B ──┘
比较项dup(63)重新 open
新文件描述符是是
新打开文件描述否是
共享文件状态标志是否
共享管道缓冲区是是

例如，利用 fcntl 修改 fd 3 的 O_NONBLOCK 标志，不会因此改变独立打开的 fd 63 的对应标志。但从任一描述符读取数据，都会消耗同一管道缓冲区中的字节，并不会获得两份数据。

六、从现象到本质

这个实验揭示了三个不同层次：文件描述符是进程中的整数索引；打开文件描述是内核中记录打开状态的对象；管道对象则是实际承载数据的共享资源。共享底层资源，不意味着共享打开文件描述；共享打开文件描述，也不意味着文件描述符编号相同。
